# 导入：把别人的导图变成我们的三种图型之一

代码在 `backend/app/importing/`，界面入口是顶栏的「导入」按钮
（`frontend/src/components/ImportMindmap.vue`），接口是
`POST /api/mindmaps/import`（multipart，只解析不落库）。

这条功能的判据是"**能导出什么就能导入什么**"，但这句话现在有两档，混在一起讲会
误导人：

| 口径 | 格式 | 含义 |
| --- | --- | --- |
| **无损往返** | 本仓库 JSON | 导出 → 导入之后，除节点/边/关系的 id（重新生成）与 `source_refs`/`source_usage`（故意清空）之外，**逐字段相等**，含图型 |
| **形状能还原、内容有损** | Markdown（本仓库导出） | 形状靠文件头那一行 `<!-- genai-mindmap: shape=… -->` 还原，树/鱼骨/流程**都回原形**；文字、阶段、两层边、`detail`、鱼骨的 `category` 与骨根 `note` 都在。丢的是视觉字段、`role`、`note` 与 `label` 的区分（阶段根与骨根除外）、以及"边上既有文字又有 `kind`"时的那一半 |
| **有损往返** | OPML / PlantUML / XMind / FreeMind / 手写的 Markdown | 结构能读回一棵树、文字、`detail` 在；**形状退化成树**，视觉字段与容器名有不同程度的丢失 |

所以"六种格式闭环"这句话**不成立**，它已经从 `test_import.py` 的说明里撤掉。
"闭环"暗示"往返之后什么都没丢"，而事实是上表那三档：唯一无损的是 JSON，markdown
能还原形状但仍是有损，其余四种连形状都不认。判据本身没有变松——变清楚的是
"往返一次会掉什么"，逐格式写在下面的矩阵里。

## 判据：哪些格式认完整结构，哪些只产树

一个 `.xmind` 文件里没有"图型"这个概念——它就是一棵树。所以只有三条路可走：

- **按格式判（采纳）**：本仓库的 JSON 认完整结构（顶层键 `root` / `problem`+`bones` /
  `stages` 三者互斥，判据与契约 `DiagramContent` 的判别同源）。
- **按文件自述判（采纳，仅 Markdown）**：本仓库导出的鱼骨/流程 markdown 第二行写着
  `<!-- genai-mindmap: shape=fishbone -->`，导入读它。**这一行是导出写的，不是猜的**
  ——所以它不违反下一条。
- **让用户选**（"当成树 / 鱼骨 / 流程"）：没采纳。外部文件里没有这个信息，问用户
  等于让他替文件回答一个它没说过的问题；而选错之后画布会按另一种形状去读同一份
  数据，表现是"骨只有一根"或"阶段没有边"这类说不清来源的错误。

拒绝第三条路（**从形状硬推断**）的理由只有一句：外部格式没有图型概念，硬推断是
编造。XMind 的 `structureClass` 里确实有 `fishbone` 这个词，但它描述的是**画法**，
不是"这六条一级分支就是人机料法环测"——`xmind.py` 因此只把它读成 `layout` 与
`diagram_type` 两个字段（都只影响显示），**形状仍是树**。那批图导进来之后
`diagram_type` 写着 `fishbone` 而形状是树，这是**如实**的：文件里就这么多信息。

markdown 的标记之所以能算"文件说的"而不是"我们猜的"，判据是**它由本仓库的导出
写出来**：一份手写大纲里不会出现那行注释，删掉它只是退回按树导入。标记的样子与
理由见 `export.service.shape_marker`。

## 格式矩阵

| 格式 | 导出 | 导入 | 导回来是什么形状 | 往返之后还剩什么 | 丢了什么 |
| --- | --- | --- | --- | --- | --- |
| JSON（本仓库序列化） | ✅ | ✅ | **原样**：树→树、鱼骨→鱼骨、流程→流程 | 结构、`label`/`note`/`detail`、颜色/图标/折叠/`role`/`style`/坐标、图型、布局、主题、阶段与阶段内边、跨节点关系（含 `provenance`） | `source_refs` / `source_usage`（**故意**清空）、各种 id（重新生成） |
| Markdown 缩进大纲 | ✅ | ✅ | **原样**（本仓库导出的那份：第二行的形状标记说明是哪一种） | 结构、标题、`detail`（节点行下面的 `>` 引用块）、阶段与阶段标题、附加边（label 与它里面的括号，且没有 label 时写出 kind 中文说法的那一半）、鱼骨的骨与原因、鱼骨的 `category` 与骨根 `note`（骨行下面的 `<!-- genai-mindmap: bone {…} -->`） | `note` 与 `label` 的区分（合成一句塞进 `label`，阶段根走 `标题｜正文`、骨根走骨注释）、颜色/图标/`role`、边上**同时**有 label 与 kind 时的那一半（一个后缀槽装不下两个）；**手写的 markdown 没有标记，形状仍是树** |
| OPML 2.0 | ✅ | ✅ | 树 | 同上，另加 `detail`（`_note` 属性，**导入侧读回**） | 同上 |
| PlantUML mindmap | ✅ | ✅ | 树 | 结构、图型（文件头注释）、附加边、`detail`（`' 说明：` 注释，**导入侧读回**） | 同上，另加：正文里的 `*` 已被导出成 `·`、说明里的 `-->` 被压成 `→`，都不可逆 |
| XMind（`.xmind`，新版 `content.json`） | ✗ | ✅ | 树 | 结构、`title`、备注、`structureClass`→布局、`svg:fill`→颜色、marker→图标 | 无导出出口；`structureClass=fishbone` 只落成 `diagram_type`，形状仍是树 |
| XMind 8（`content.xml`，含单独拖进来的 xml） | ✗ | ✅ | 树 | 同上（旧版样式表 `styles.xml` 不读） | 同上 |
| FreeMind（`.mm`） | ✗ | ✅ | 树 | 结构、`TEXT`、`COLOR`、`<icon>`、`<richcontent>`、`FOLDED` | 无导出出口；`POSITION`/`<attribute>`/`LINK` 丢掉 |

一句话读法：**只有 JSON 这一行能说"往返之后一模一样"**；markdown 那一行能说
"形状还认得出来，内容丢一部分"；其余六行（含两种 XMind）都是"能导进来、能看懂、
形状会变"。这是格式能力所限，不是实现偷懒——树以外的两种形状原本连"这几条是骨"
都没有语法可写，现在靠约定 + 一行标记才有了落点。

`detail` 那一列值得单独说一句，因为它此前是文档与代码打架的地方：三种文本格式
**导出时都写了** `detail`（引用块 / `' 说明：` / `_note`），而 OPML 与 PlantUML
的导入侧当时一个都没读。旧矩阵一半写"detail 在"、一半写"导入侧不读它"，两句都是
真的，合起来就是自相矛盾。现在两条路都读回来了（`opml._detail`、
`puml._NOTE`），所以矩阵只有一个说法。

## 两个 Markdown 解析器：缩进的实测

同一份导出的 markdown，两个主流解析器给出的树可以不一样——这决定"导出的文件在别处
打开时是不是同一张图"，所以这里的判据不是"能渲染"，而是**两边嵌套正确**。

缩进按层改**4 个空格**（鱼骨与流程）之后，Python-Markdown 3.11 与 CommonMark
（`markdown-it-py` 4.2.0 的 `commonmark` preset）对同一份文件给出同一棵树：

```
- 为什么报销要 11 天
    - Staff
      > 骨的生成说明
        - 审批的人不在
```

Python-Markdown：

```html
<ul>
<li>为什么报销要 11 天<ul>
<li>Staff<blockquote>
<p>骨的生成说明</p>
</blockquote>
<ul>
<li>审批的人不在</li>
</ul>
</li>
</ul>
</li>
</ul>
```

CommonMark：

```html
<ul>
<li>为什么报销要 11 天
<ul>
<li>Staff
<blockquote>
<p>骨的生成说明</p>
</blockquote>
<ul>
<li>审批的人不在</li>
</ul>
</li>
</ul>
</li>
</ul>
```

两条硬规则，都是从实测里得出来的（不是从规范里推出来的）：

1. **子列表缩进 ≥ 4 格**。Python-Markdown 按 `tab_length=4` 判层级，2 格不够——
   `- 骨` 比鱼头深 2 格时它认不出这是子列表，把鱼头与六根骨画成同一级。
   CommonMark 从 2 格起算，所以 2 格在它那一边是对的、在另一边是错的。
2. **`detail` 的引用块缩进 = 节点行 + 2 格，不能更多**。`+2` 两边都认；`+4`
   Python-Markdown 会把它当缩进代码块，`>` 变成字面文本（`&gt; 骨的生成说明`）。
   所以 `_markdown_quote` 的 `pad + "  "` 这条规则与层宽无关，改层宽时不要跟着放大。

**已知未修：树的 markdown 仍是 2 格缩进。** 它在 Python-Markdown 下会把根与一级
分支画成同级——与鱼骨改之前一模一样的表现。没改的原因是两条约束撞在一起：
`tests/test_export.py::ByteIdenticalTest` 把树的输出逐字节钉死，本轮修复的边界也
写着"树的既有行为逐字节不变"。要改就是三处（`_markdown_tree` 的 `pad`、那两条
逐字节断言、`test_edges.py` 里按 `  - 付款` 定位的一处），是一次独立的改动。

`tests/test_import.py` 里每种格式都有往返用例，但它们的**判据分三档**：
`ThreeShapeRoundTripTest` 比的是完整 dump（除 id 与引用）；markdown 的三种形状比
"形状 + 阶段/骨 + 两层边"（`ShapeJudgeTest` / `FlowMarkdownTest`）；`*RoundTripTest`
比的是 `shape()`（结构 + 文字）。刻意留下的那处不等价——带 `note` 的节点往返之后
`note` 变成 `label`——由 `test_note_text_survives_as_label` 明确钉住。

## JSON 往返：逐字段相等怎么保证

三件事各守一段，缺一段就有一类字段会被静默丢掉：

1. **形状按顶层键判，不看 `diagram_type`**。`json_import._shape_of()`：有 `stages`
   数组 → 流程；有 `bones` 数组或 `problem` 键 → 鱼骨；其余 → 树。`diagram_type`
   在这一层的职责是"产物自述"（导出文件头、界面文案），拿它判别会让库里那批
   "标着 fishbone、形状是树"的旧记录走进不存在的分支。
2. **字段逐个挑，但每个契约字段都有落点**。`_raw_node()` 覆盖 `Node` 的全部字段
   （含 `role` / `style` / `pos` / `expandable`），`_raw_containers()` 覆盖
   `bones[i]` 的 `category`/`color`/`icon` 与 `stages[i]` 的 `id`/`edges`。
   "挑"是为了容忍用户手改出来的多余键（`extra="forbid"` 会让整份 422），而"全覆盖"
   由 `test_*_roundtrip_is_field_by_field` 钉住：导出加了字段而导入不认，那条用例
   立刻红。
3. **校验一定要过**。归一化末尾**真的构造** `MindMapContent` / `FishboneContent` /
   `FlowContent`，它们自己的 `model_validator` 会把"非法图"拦在这里（否则它会在
   画布上炸：dangling 边让 Vue Flow 白屏、重复阶段 id 让点一下跳到另一个阶段）。
   拦在导入这一层的代价是 400 + 一句可读的话；放过它的代价是用户点开就白屏。

三处刻意**不**原样保留，每一条都有理由：

- `source_refs` / `source_usage` **清空**（`normalize` 第 ⑤ 条）：外部引用指向的是
  **别人那份原文**的字符偏移，`source_id` 在新环境里不存在。带进来直接让
  `validate_tree` 抛"引用的来源不在 source_usage 中"，整份 422。
- 节点 / 边 / 关系 / 阶段的 id **重新生成**：外部 id 与库里碰撞的后果是"引用了
  另一个节点"这种完全静默的错。所以"逐字段相等"的可实现定义里，id 一律按端点
  指向的**标题**比较（见测试里的 `canonical()`）。
- `provenance` **照收文件的值**，只有文件没写时才记 `import`。这是这条改动里唯一
  一处语义修正：对 markdown/opml/puml 一律记 `import` 是对的（它们没有这个字段），
  对自家 JSON 就是丢字段——`user` / `ai` 是"这条关系谁连的"，属于图的内容。

`role` 是这一轮补上的一个真实空洞：`Node.role` 是流程图判定节点画菱形的唯一依据，
而它此前**不在** `_raw_node()` 读取的字段里——导出一张流程图再导回来，判定节点会
全部退化成普通方块，而 `branch` 边还在，于是画布上「是 / 否」两个出口看起来是从
一个方框里分出来的。

## 五件边界处理（`normalize.py` 的唯一实现）

| 事项 | 做法 | 为什么 |
| --- | --- | --- |
| id | 全部用 `agent.ops.new_node_id` 重新生成，建 `旧 id → 新 id` 映射重建边/关系 | 外部 id 可能是 `1`、UUID 或我们自己的 `n_xxx`，与库里的碰撞后果是"引用了另一个节点"这种完全静默的错 |
| 节点数 > 1000 | **BFS（层序）保留前 1000 + warn** | 见下一节 |
| 深度 > 8 | 截断子树 + warn | 契约硬边界，超了 `validate_tree` 会整份 422。深度按**每棵子树**从 1 数（一根骨挂在主骨上，但画布上它是一列自己的） |
| 单节点 > 50 子 | 截到 50 + warn | `Node.children` 的 `max_length` 是硬边界（`MAX_NODE_CHILDREN`） |
| `label` | 只套契约上限 **200**，不套生成侧的 16 | 用户手写的长标题被截到 16 字不可接受；16 是"模型生成时画布放得下"的口径，不是导入的 |
| `role` | 四个合法值照收，其余丢掉 | 文件自造的角色画出来只是方块，而留着它会让整份导入 422 |
| 视觉字段 | 精确表映射（`colors.py`），映射不到就丢 | 猜错的颜色/图标用户改不回来，也说不清出处。hex 认得出就留在 `NodeStyle.color`（不渲染、保存不丢） |
| `source_refs` / `source_usage` | **一律清空 + 一条 warn** | 见上一节 |
| 骨的类别 | 空 → 「（未分类）」；超 40 字截断；**重复的加序号**（`人（2）`） | 契约要求类别非空且唯一，两者都是硬拒。丢一根骨是丢一整棵原因子树，改名只动一个词 |
| 阶段数 > 20 / 骨数 > 6 | 截断 + warn | 两者都是**顶层数组**，多出来的在画布上没有位置（契约 `max_length` 硬边界） |

超限**永远不整份拒绝**：用户导一张 XMind 进来，因为多了几个节点就什么都不给，
比少几个节点糟得多。

## 截断顺序：树按层序，容器**按层轮转**

树只有一棵，BFS 的含义没有歧义。鱼骨有六根骨、流程有二十个阶段，那一千个额度怎么
分有三条路，选的是第三条：

- **逐个容器截满再下一个**：第一根骨吃掉 1000，另外五根整根消失。**否决**——鱼骨图
  的读法本身就是六类成因并列对照，砍掉五类之后那已经不是一张鱼骨图，而是一棵长得
  像鱼骨的树。流程图同理：阶段是主轴，少一个阶段整条流程就断了。
- **每层各容器平均分**：要额外写一套配额分配，而且"平均"在容器大小悬殊时反而更糟
  （一根 3 个原因的骨与一根 800 个原因的骨各分 500，后者被砍掉的正是最该保留的
  部分）。**否决**。
- **多源 BFS（采纳）**：把六个容器的根同时放进队列，层序出队。第 1 层是六根骨，
  第 2 层是每根骨的第一个原因（按容器顺序），第 3 层是每根骨的第二个原因……
  **层内按容器轮转，整体仍是层序**。

它与树上那条 BFS 是同一个立意：保留"每一个一级分支"，被裁掉的是各支**最深处**——
那是"没读到这里"，不是"这里没有了"。实现上没有额外的轮转代码：多源初始化之后，
队列的出队顺序本来就是"层序 + 层内按入队顺序"，而入队顺序就是容器顺序。策略是队列
的性质，不是一段 if（见 `normalize._Builder` 的 docstring，用例见
`ContainerBfsTest`）。

代价与树那边一样，写在 warning 里：**同一层里靠后的容器先被裁**。所以一份 1806 个
节点的鱼骨图导进来，六根骨与它们的一级原因全在，第 3 层只有前几根骨有内容。

## 格式判定：`detect_format(filename, head_bytes)`

```
1. zip 魔数（PK\x03\x04 / 05\x06 / 07\x08 / 06\x06）  → xmind（候选）
2. 强内容特征：<opml / <map>+<node / <xmap-content / @startmindmap / { 或 [  → 内容赢
3. 扩展名（.json/.md/.opml/.xmind/.mm/.puml…）          → 用它
4. markdown 的嗅探（# 标题 / - 项）                      → 只在没有扩展名时兜底
5. 都不成立                                              → unsupported_format
```

两处刻意的顺序：

- **zip 魔数压过 `.json` 扩展名**（题目里的判据）。zip 里到底有没有 XMind 的
  `content.json`/`content.xml` 只有打开才知道，所以 `xmind.parse` 会做二次确认；
  确认失败报 `unsupported_format`（"这是 zip，但里面没有 XMind 的内容表"），
  而不是 `parse_failed`——那不是文件坏了，是类型不对。
- **markdown 排最后**。`* 根` / `- 项` 在聊天记录、笔记、CSV 里都常见；让它推翻
  扩展名的后果是：一个缺 `@startmindmap` 的 `.puml` 被当成 markdown 读成一份
  **层级丢失**的大纲（`** 子` 在 markdown 里是根的同级项），用户拿到一张结构错乱
  却"导入成功"的图。

## 脏数据：堵住了什么、还剩什么

已经堵住的（都有用例）：

- **NUL / ESC 等控制字符**（`unicodedata.category == "Cc"` 折成空格）——否则
  label 里会带 `\x1b[31m` 这种终端控制序列。
- **压缩炸弹**：XMind 单个成员解压后上限 20MB（先看中央目录的 `file_size`，
  读完再按实际长度复核）。
- **实体膨胀**：带 `<!DOCTYPE` / `<!ENTITY` 的 XML 直接拒（标准库会展开内部实体，
  1KB 能撑到 GB 级）。
- **解析期节点上限**：5000（`RAW_NODE_HARD_CAP`），四个文本解析器在**收集阶段**
  就截，避免"先把几十万个列表项装进内存再裁"。多容器的 JSON 也一样：`bones` /
  `stages` 共用一个 `Budget`。
- **深度递归**：所有树遍历用显式栈；`json.loads` 的 `RecursionError` 被 catch
  成 400。
- **循环引用**：树结构不可能成环（逐层嵌套，json 的重复对象各自独立）；
  `edges`/`relations` 成环是**合法**的（回退线），契约允许。
- **文件大小**：10MB 上传上限。
- **dangling / 自环 / 重复边**：进契约前丢掉 + warn（dangling 会让前端白屏）。
  流程的阶段内边还多一道**跨阶段过滤**：端点不在本阶段里的边直接丢，否则契约层
  硬拒整份图。
- **空 `stages`**：`unsupported_format`（"流程图至少需要一个阶段"）。不能让它走到
  归一化末尾变成一句"导入结果没能通过契约校验"——那句话指不回是哪一部分的问题。

还剩下的（会崩的地方说清楚）：

- **`note` / `detail` 超 2000 字**被截断（有 warn）。不截的话整份 422，所以这是
  两害相权。
- **双向文本控制符**（U+202E 等，Unicode `Cf` 类）不清洗。它们不可见但不破坏
  渲染——最坏情况是某个标题在画布上"从右往左"显示。清掉它们的风险是误伤合法的
  RTL 文本（阿拉伯语 / 希伯来语），所以留给人眼判断。
- **零宽字符**（U+200B / U+FEFF）保留。它们不破坏布局，但会让"看起来一样的两个
  标题"在搜索时不相等。
- **同一 label 的重名节点**：markdown/opml/puml 的边端点按文字匹配，重名时连到
  **第一个**（层序）。这是格式能力所限（文本格式里节点没有 id），不是 bug，
  但导入一张同名的图时那几条边可能连错位置。
- **`options` / `theme` 之外的布局语义**：`logic` / `timeline` / `fishbone` 会被
  保存下来，但前端只渲染 tree / vertical，所以"逻辑结构图"导入后看起来是一张
  普通思维导图。这是既有的渲染口径，不是导入引入的。
- **XMind 的 `detached`（游离主题）**：丢掉 + 提示。它们不属于任何父节点，而模型
  里每个节点都必须挂在树上；塞到根下会假装它们是根的分支。
- **markdown 的多级标题现在是容器**（`### 1. 提交` 是一个节点，它下面的列表项是它的
  内容）。补这一条之前，第一个 `#` 之后的所有 heading 都被 `continue` 跳过——流程
  导出用它们当阶段标题，于是阶段名整段消失、那几行边清单反倒变成了节点。**它有一处
  例外**：第一个标题永远只是导图标题，所以"先写列表项、再写 `## 某节`"的文件里，
  那个 `##` 会被当成标题而不是容器。
- **opml 里的二级以下标题**：仍然跳过（不是边、不当节点）。opml 的容器是 `outline`，
  不是 heading；`<outline>` 的层级已经表达了结构，额外的 heading 只是正文。
- **边上同时有 label 与 kind**：markdown/puml 的边行只有一个后缀槽（
  `- 甲 → 乙（驳回）`）。导出时 label 优先（见 `export.service._edge_suffix`），
  所以那条边的 `kind` 在往返之后落不下来——一条 `loop` 边会画回实线。没有 label 的
  边反而能把 kind 带过去（导出写 `（回退）`，导入读回 `loop`）。
  **标签自己的括号不算这一类**：`Rejected (missing file)` 与 `驳回（材料不全）`
  都能原样往返（导入侧按括号深度切后缀；导出在标签的圆括号配不平时换一对分隔符
  `〔…〕`，见 `_wrap_edge_suffix` / `_split_edge_suffix`）。
- **`role`**：markdown 里没有它的槽位。流程图的判定节点往返之后不再是菱形，除非
  用 JSON。这是"文字槽位有限"的另一处，写在上面的格式矩阵里。
- **树的 markdown 是 2 格缩进**：在 Python-Markdown 下会画成同级列表。这是
  **既有行为**（被 `ByteIdenticalTest` 与"树逐字节不变"的边界冻住），不是本轮
  引入的；实测与改法见上面「两个 Markdown 解析器」一节。

## 能修的和装不下的：一条分界线

往返损失分两类，处理方式不同——混在一起讲的时候，两类都会被写成"格式所限"，
于是第一类永远没人修。

**能修、已经修了的（都是"导出写了但导入没读"或"导出写得有歧义"）**：

| 损失 | 原因 | 修法 |
| --- | --- | --- |
| 鱼骨的 `category` 与骨根 `note` | 文字槽被 `label` 占着，两个字段没有落点 | 骨行下面一行 `<!-- genai-mindmap: bone {json} -->` |
| 边标签带括号时整条边丢失 | 后缀正则不许括号套括号，标签认不出→端点对不上 | 从右端按括号深度切；配不平时导出换一对分隔符 |
| `&lt;token&gt;` 往返变成 `<token>` | 导出只转 `<`/`>`、不转 `&` | 导出先转 `&`，导入按相反顺序还原 |
| OPML / PlantUML 的 `detail` | 导出写了 `_note` / `' 说明：`，导入侧一个都没读 | 两条路各加一个读取点 |
| 鱼骨在 Python-Markdown 下画成同级 | 2 格缩进不够它判层级 | 每层 4 格（树的同一问题待决策） |

这一类没有一条是"Markdown 装不下"——每一条都有位置，只是那个位置当时要么空着
（没写）、要么写着歧义格式（写坏了）。

**格式本来就装不下的（写进矩阵，不硬修）**：

| 损失 | 为什么装不下 |
| --- | --- |
| `note` 与 `label` 的区分（树节点） | 三种文本格式都只有**一个**标题槽。加第二个槽就得再造一套行约定，而收益是"这两个字段分别是什么"——那本来就该用 JSON |
| 边上同时有 `label` 与 `kind` | 边行末尾只有**一个**后缀槽。两个都写会得到「驳回（回退）」，读起来像同义重复；要都保住得给边行定结构化语法 |
| `role`（判定节点） | markdown 的列表项没有"这是菱形"这个概念。它不是文字，是一个渲染决策 |
| 颜色 / 图标 / 折叠 / 坐标 | 同上：都是视觉字段，文本大纲没有槽位。OPML 有 `_note` 但没有公认的颜色属性 |
| `*` → `·`（puml）、`-->` → `→`（puml 说明） | PlantUML 的 mindmap 语法把 `*` 当层级标记、把含 `-->` 的注释当边。除非放弃"文件能被 PlantUML 解析"，否则这两个字符没有第二种写法 |
| 重名节点的边端点 | 文本格式里节点**没有 id**，端点只能是文字。重名时"连到哪一个"在文件里无法表达 |
| 鱼骨 / 流程的形状 | markdown 与 OPML 里都没有"这是骨"的语法。**这一条已经用形状标记绕过去了**——但那不是"装得下"，是我们自己定了一个约定，所以只对本仓库导出的文件成立 |

判据可以压缩成一句：**文件里有位置、只是没写或写歧义的 → 修；文件里根本没有那个
位置的 → 写进矩阵。** 前者修完往返就守恒，后者再修也只能换一种损失方式。
