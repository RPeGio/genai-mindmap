# 全塞还是按支检索：一次实测与一条被改掉的提示词

这份文档回答两个问题，都是**在本仓库的链路上实测**出来的，不是引用的外部结论：

1. 材料正文整份塞进 prompt（下称**全塞**，`tools.FULL_TEXT_MATERIAL_CHARS` 那条闸），
   在「材料 → 一张带引用的思维导图」这个任务上，比按支检索更好吗？
2. 上下文长到什么时候开始"看得到却用不上"？

复现：`cd backend ; python scripts/measure_incontext.py`（三档 × 两条路 × 两次采样，
约 5 分钟、24 次模型调用），只重算表用 `--report`。原始产出落在
`backend/data/measure_incontext/`（被 `.gitignore` 的 `data/` 忽略，不进仓库）。

> 这份文档**不写进 `docs/RAG-DECISIONS.md`**：那个文件本身是检索评估套件的材料
> （`scripts/eval_cases_manual.py` 的 `MANUAL_SOURCE_HASHES` 钉着它的正文指纹），
> 改一个字就会让跨文档套的 1583 段标注区间失效。要改它，得先重读材料、重标区间、
> 再写回新指纹——那是另一件事。

## 实验设计

材料是自造的、可控的：同一份制度正文按目标字数扩充（前面的段落逐字相同，**句级无
重复**——重复会让模型抄出的引文在多处命中，`verify_source_refs` 判成待核，把"引用
存活"这项指标污染成"材料重复度"）。三个自造编号分别埋在**第一段、正中间那段**
（位置 0.49–0.50）、**最后一段**：

| 位置 | 编号 | 内容 |
|---|---|---|
| 开头 | `KP-OPEN-1187` | 依据哪份批复制定本办法 |
| **正中** | `KP-MID-4429` | 批量导出由**数据安全与合规委员会**统一登记，备案号 |
| 结尾 | `KP-END-9032` | 附则的修订依据 |

主题问的是**中间**那个编号（"数据导出审批：批量导出由谁登记、备案号是多少"）——
"lost in the middle"最容易丢的位置。

三条对照条件：三档长度（1 万 / 5 万 / 15 万字）、两条路（按支检索 / 全塞）、
每格两次采样。两条路**只差一个常量**，材料、主题、骨架、模型（`deepseek-flash`）
逐字相同；材料**不带 markdown 标题**，所以两条路的骨架调用输入也逐字相同。

## 四件事，按可信度排序

### 1. 覆盖是全塞稳定且唯一的收益

六次运行里，检索**一次都没覆盖到结尾那段**（`✗✗ / ✗✗ / ✗✗`）；全塞六次里覆盖了
五次。这不是"模型没读到"，是检索根本没召回——按支检索的 query 是分支标题本身
（`_search_branch` 的三组消融选了这一版），而结尾段（附则）与任何分支标题都不重合，
`top_k=3` 永远轮不到它。

这就是 `_search_branch` 那个 28.8% 覆盖率上限在产出上的样子：**一整套内容静默缺失，
而树看起来是完整的**。

### 2. "中间的事实"两条路都没稳定丢——但这不能证明什么

全塞 6/6 命中中间那个编号，检索 5/6（5 万字第一次采样丢了）。所以这批数据**没有**
复现经典的 lost-in-the-middle，反而在 5 万字档上"全塞更稳"。

原因必须说清：5 万字那次检索的丢失是**召回失败**（`top_k=3` 没捞到中间段），不是
注意力问题。而中间段与主题强相关（主题问的就是它），所以它对检索是"必中"的题、对
全塞是"正中"的题——两个效应方向相反、互相抵消。**这组数据不能用来证明"长上下文
不会丢中间"，也不能用来证明"检索一定召回得到中间"**，它只能说明在这个具体的题目
上两者打平。

### 3. `declared → kept` 的差额不是"引文抄错了"，是节点被裁

这一条是回头查原始响应才纠正的，差点写反：

- 全塞档的 `kept` 恒等于 `declared` 减去 `TREE_CLIPPED_TO_INITIAL` 裁掉的节点上的
  引用。四次有裁剪的运行差额 2 / 5 / 2 / 10，四次无裁剪的差额 0——**无一例外**。
- 逐字校验把 61 条结构响应里的引用**一条都没剔**（`quote in 原文` 全为真）。

也就是说：**全塞并不降低引用准确率，它让模型把树写满**（79–80 个节点，贴着
`INITIAL_MAX_NODES=80`），于是尾巴被裁、尾巴上的引用跟着消失。检索那一路产出
62–75 个节点，从不触发裁剪，所以 `kept == declared` 恒成立。

这个副作用有真实代价：用户拿到一张"内容更全、但末尾几块连同出处一起没了"的图。
`partial` / `TREE_CLIPPED_TO_INITIAL` 会如实标出来，但那不是用户想要的形状。

### 4. detail 略短、引用密度持平

- **detail 均长**：全塞均值 104.2 字，检索 111.6 字（-7%）。没有一次触到 40 字红线，
  也没有一条空话填充。这一项的单次波动本来就有十几字（历史实测），-7% 属于弱信号。
- **引用密度**：全塞 0.55–0.64；检索 0.60–0.99。看起来检索更高，但检索那一路自己
  就抖得厉害（1 万档两次采样 0.63 与 0.99），**这一项不足以判定优劣**。第一轮只跑
  一次采样时读到"全塞密度明显更低"，那是采样噪声。

## 阈值定在哪、为什么

`tools.FULL_TEXT_MATERIAL_CHARS = 50_000`（约 3.3 万 token，占 200k 上下文的 17%）。

- **覆盖收益在 ≤5 万字是稳的**：1 万与 5 万档各 2/2，检索 0/4。
- **代价从 5 万字档就开始了**：两次都触发裁剪（7–9% 的节点被裁）。
- **15 万字档两边都不好**：全塞自己丢了一次中间、一次结尾，同时仍然被裁；检索依旧
  0/2 覆盖。拐点在 5 万–15 万之间，取**低的一端**。

物理上限是 `CONTEXT_TOKEN_LIMIT`（200k token）/ 1.5 字每 token ≈ 30 万字，但注意力
与裁剪都先于物理边界失效——这个数不是按"装不装得下"定的，是按"装得下之后产出还像
不像样"定的。

## 一条被实测改掉的提示词写法

全塞的第一版把引用规则只放在 **system** 里（`FULL_TEXT_EVIDENCE_RULES`），结果是：

- 1 万字档 **declared = 0**——模型把材料中间那个备案号一字不差抄进了 detail（内容
  用上了），却一条 `source_refs` 也不写；
- 同一批材料走按支检索时是 72/72。

把它挪到 **user 末尾、正文之后**（紧邻输出位置）后，同一条路变成 49/49。

这与 `_detail_ask` 结尾那句自查、flowchart 的 `role` 说明踩过的是同一个坑：**模型对
紧挨着输出位置的那句话最敏感**。而全塞把上万个字塞在 system 与输出之间，那句话就
失效了——这不是"多提醒一遍更保险"，是位置问题。`tests/test_full_text_material.py`
把这条修复钉在**位置上**（`user.rindex("source_refs") > user.index(<正文>)`），而不是
钉在"两处都有这句话"上。

## 那条 93 vs 59 的证据，可用范围比它看起来窄

外部那组一手实测（64 份文档全塞进上下文 **93 分**，切成 1583 段做检索 top5 只有
**59 分**）**没有在我们这条链上复现**。它不是错的，是任务不同：

- 那组实验的产出是**一段答案**，"用没用到某段材料"只影响那一句话的分数；
- 我们的产出是**一棵带引用的树**，"每条出处能不能逐字核实""树有没有被裁短"本身就是
  交付物的一部分。

所以"RAG 过度设计"这个怀疑，在这条链上**部分成立、部分不成立**：

- **不成立的那一半**：全塞不是"更省事而且更好"。它换来覆盖，付出的是裁剪（树被砍短）
  与略短的说明；引用密度与准确性都没有提升。
- **成立的那一半**：检索的覆盖率上限确实是结构性的（结尾段 0/6），它不由模型好坏
  决定，而由"分支标题能不能命中原文"决定。想补这一块，全塞是最直接的办法。
