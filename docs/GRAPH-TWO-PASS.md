# 图谱两段式：用知识图谱定节点，而不是章节骨架

> 一次实验的记录：把生成链路从"章节骨架 → 每支检索 → 结构 → 说明"改成
> "图谱 → 结构 + 关系 → 说明"，然后在同一批材料上跑 A/B。
> **结论先说：关系线拿到了、墙钟快了一倍，覆盖率没有上去、detail 掉了一半。**

## 1. 它要解决什么

三段式的骨架是**用材料自带的章节标题定的**（`_skeleton_outline` → `heading_outline`）。
这条路有两个天花板，都是实测的：

- **覆盖率被"标题能不能命中原文"卡住**。骨架定出分支后，每支拿**分支标题**去检索
  （`_branch_query`），召回上限由标题与材料用词的对齐程度决定：实测 28.8%，把标题
  换成"背景 / 现状 / 方法"这类通用词时掉到 15.4%（`docs/RAG-DECISIONS.md` 第 5 节）。
- **标题不是内容**。章节标题说的是"这一节叫什么"，不是"这一节里有哪些概念、它们
  怎么相互依赖"。关系（A 依赖 B、C 是 D 的一部分）在标题层面根本不存在，所以三段式
  产出的树天然只有父子层级，`relations` 字段一直是空的。

## 2. 两段怎么切

```
第一段  图谱 → 节点结构 + relations     一次调用
        输入：本次这几份材料的图（头部实体 + 它们之间的边）+ 按实体名检索到的证据
        输出：{"title": …, "root": {…}, "relations": [{source, target, kind, why, confidence}]}
第二段  只写 detail                    一到两次并发（复用 _fill_details）
```

原三段式是三次调用（骨架 + 结构 + 说明），两段式是两次。**省掉的正是骨架那一次**
——一级分支不再由它定。

### 第一段的 system 关键段

```
这次**不用章节标题定骨架**，一级分支从 user 消息里那张图谱来：
- 根节点是主题本身；
- 一级分支从「最重要的概念」里挑，优先挑**连接数高**且彼此不重复的；
  概念之间是整体与部分的关系时，合成一条分支（用整体当分支名），不要拆成两条；
- 每个一级分支下面写它的具体要点；要点可以是图上与它相连的概念，
  也可以是材料里支持这个分支的细节；
- 图谱只是**选材依据**，不是要照抄的清单：图上没有但材料里有的内容照样写。

**另外给出一组跨分支的关系**（`relations` 数组，与 root 同级）。
每条关系的形状：{"source":"节点id","target":"节点id","kind":"depends_on",
"why":"一句话说清为什么","confidence":0.8}
四条规矩，缺一条这条边就不该写：
1. **只能连不同一级分支下的两个节点**：同一个父节点下面的两个节点之间有关系，
   树已经表达了，不要再画线。
2. `kind` 只能取这六个值之一：depends_on / causes / conflicts / part_of / refines / references。
3. `why` 必须写，一句话（不超过 60 字）说清**这两个节点为什么会有关**。
4. `confidence` 是你对这条边的把握（0–1 的小数）。
最多 30 条。没有值得连的关系就给空数组 []。
**位置**：`relations` 与 `title`、`root` 放在**同一个对象**里（最外层），
**不要**把它放进 root 里面。
```

最后那条"位置"是实测补的：第一版只说"与 root 同级"，模型把 `relations` 塞进了
**root 里面**（它把 root 当成"主体"，于是"同级"被理解成"和 root 的字段同级"），
而 `Node` 是 `extra="forbid"`，整次生成直接判废。`_generate` 里另有一道兜底把 root
内部的 relations 摘出来，但提示词这一句才是让它第一次就写对的东西。

### 第一段的 user 长什么样

```
主题：这个多智能体思维导图系统的架构与取舍

这次**不按材料章节分**：一级分支请从下面这张图谱里挑（挑法与关系的写法见 system 的规则）：
【图谱：材料里最重要的概念（按连接数排序）】
- w1（事件） 连接数 20
- mindmapcontent（其他） 连接数 16
- service.py（其他） 连接数 16
- sqlite（概念） 连接数 16
  …（共 60 个）

【图谱：这些概念之间的关系（箭头是方向，括号里是材料里的说法）】
- snapshot → mindmapcontent：包含
- w1 → tls：不启用
  …（共 51 条，按"被几段材料独立抽到"降序）

一级分支不超过 6 条，每条不超过 16 字，彼此覆盖的范围不重叠，按逻辑顺序排列。
一级分支给一个 color（…）与一个 icon（一个 emoji）。

下面这些是本次按图谱里的概念检索到的原文：
第 1 个概念「w1」的检索结果（evidence 数组）：
[…]
```

顺序即权重：先图（选材依据），再证据（事实依据），最后才是要求。

### 检索的 query 换了

三段式发的是**模型猜的分支标题**，两段式发的是**材料里真实出现过的实体名**
（图的头部 12 个）。这是覆盖率能上去的第一条路（第二条是结构那一次直接拿到了
整张子图）。两段式**不做 query 扩展**：`plan_branches` 的价值在于"骨架标题是模型
臆造的通用词"，而实体名本身就是原文词汇，再花一次模型调用把真词换成猜的词，方向是反的。

## 3. 子图怎么取（`graph_store.subgraph`）

三条 Cypher，同一个只读事务：

- **头部实体**：`MATCH (e)-[r:REL]-() WHERE $source_ids IS NULL OR r.source_id IN $source_ids`，
  按度数降序取 60 个。`$source_ids` 是"只看本次这几份材料"的闸——图是**跨材料共享**的，
  同一台机器上放过一批外卖报销的材料再生成"机器学习"，全图取头部会取到报销实体。
- **关系**：两端都在头部集合里、且同一条 scope，按 `weight`（这条关系被几段材料独立抽到）
  降序取 120 条。
- **类型**：同名不同类型取任意一个，只作提示。

`scope` 一条都对不上（材料没入过图）时**回退全图**而不是返回空——那好过"两段式直接
降级成三段式"，后者会让用户以为开关没生效。

## 4. 关系落地（`tools._relations_from`）

模型给的 `relations` 走四道过滤，每一道对应一种真的会出现的形态：

| 过滤 | 丢掉什么 | 为什么 |
|---|---|---|
| 端点 | id / label 都解析不出来的 | 契约 `_validate_relations` 对 dangling 是硬拒，留着它整张图存不回去 |
| kind + why | 缺任一 | 没有理由的边在画布上是一根说不出来由的虚线，信息是负的 |
| 同父 | 两端挂在同一个节点下 | 树已经表达了"同属一个父节点"，再加线就是 N² 条对角线 |
| 重复 | 同一对端点的同一个 kind | 画布上会出现两条完全重叠的虚线 |

然后按 `confidence` 降序取前 30，低于 `GRAPH_MIN_CONFIDENCE`（0.3）的一并不收。
id 由服务端重新编号（`rel_1`…）：模型写的 id 与节点 id 在同一个命名空间里混着，容易撞。

## 5. A/B 实测

同一批材料（`docs/` 的 `AGENT_PLAN` / `PLAN` / `ARCHITECTURE` / `RAG-DECISIONS`，
合计 66,536 字，全部入过图），同一个主题，同一个模型（`deepseek-chat`），各跑 2 次。

| 指标 | A 三段式（章节骨架） | B 两段式（图谱） | 差 |
|---|---|---|---|
| 字数覆盖（引用区间并集 / 材料字数） | 6.9% | 6.7% | **-0.2 pt** |
| 要点覆盖（句子被节点提及） | **39.8%** | **30.7%** | **-9.1 pt** |
| 实体覆盖（图实体落到节点上） | 41.0% | 39.0% | -2.0 pt |
| 节点数 | 80.0（撞上限） | 68.5 | -11.5 |
| 一级分支 | 4.0 | 7.0 | +3 |
| detail 平均字数 | **156.2** | **76.8** | **-79.4（-51%）** |
| 跨分支关系 | **0** | **12.0** | +12 |
| 墙钟 | 96.7 s | 47.6 s | **-51%** |

逐次采样：

| 组 | 次 | 节点 | 支 | 字数覆盖 | 要点覆盖 | 实体覆盖 | detail 平均 | 关系 | 秒 |
|---|---|---|---|---|---|---|---|---|---|
| A | 1 | 80 | 4 | 8.4% | 40.1% | 42.0% | 156.6 | 0 | 102.2 |
| A | 2 | 80 | 4 | 5.3% | 39.6% | 40.0% | 155.8 | 0 | 91.2 |
| B | 1 | 57 | 6 | 5.0% | 30.2% | 38.5% | 77.9 | 10 | 35.2 |
| B | 2 | 80 | 8 | 8.3% | 31.2% | 39.5% | 75.6 | 14 | 60.0 |

### 三个口径怎么算的

1. **材料字数覆盖**：节点 `source_refs` 的 `(source_id, start, end)` 区间**并集** / 材料
   总字数。取并集是因为相邻引用天然重叠 100 字（`CHUNK_OVERLAP_CHARS`），逐条相加会
   重复计算。
2. **要点覆盖**：材料按句号 / 换行切句（去空白后 ≥ 12 字），句子去空白后取所有 8 字
   滑窗，任一窗口出现在节点文本（label + detail）里就算这一句被覆盖。用 n-gram 而不是
   整句包含，是因为没有模型会把一整句原文照抄进 label。
3. **实体覆盖**：这批材料的图里有多少实体的名字出现在节点文本里。

### 怎么读这张表

- **覆盖率没有上去**。三个口径两段式都不占优，要点覆盖还低了 9 个百分点。
- **detail 掉了 51%**，这几乎可以肯定就是要点覆盖掉下来的原因：口径 2 数的是"句子被
  label 或 detail 提及"，而 A 组的 detail 平均 156 字、B 组 77 字，差一倍。两段式把
  结构那一次的注意力分给了图谱块和 relations 数组，第二段（只写 detail）拿到的证据
  更碎——12 个概念各 3 条检索结果，比 4 支各 3 条更散。
- **A 组两个采样都撞 80 节点上限**（`INITIAL_MAX_NODES`），B 组一次 57 一次 80。节点
  多本来就是覆盖率的来源之一，这一项 A 组占便宜，仍然没拉开差距。
- **两段式唯一确定的优势是 relations**：12 条 vs 0 条，而且 why 都答得上来（下一节）。
- **墙钟快了一半**：少一次调用 + 结构那一次的输出更短。

## 6. 关系质量

B 组两次采样：10 条与 14 条，`same_parent` 丢掉 1–2 条，`dangling` 丢 2 条（一次）。

kind 分布（两次合计）：`depends_on` 12、`conflicts` 4、`part_of` 3、`references` 3、
`causes` 3、`refines` 0。六种里用到五种。

抽检 8 条 `why`，逐条回材料核对：

| # | 关系 | why | 材料里有没有依据 |
|---|---|---|---|
| 1 | 语音转写改走云端 → W1 只上 IP:8080（conflicts） | 前端录音需安全上下文，与 W1 只上 IP:8080 不做 TLS 直接冲突 | 有：`ARCHITECTURE.md` 与 `PLAN.md` 都写了"录音需安全上下文 / W1 只上 IP:8080" |
| 2 | PG 迁移顺延验收后 → 图存储选 SQLite（conflicts） | PG 迁移顺延后 W1–W3 用 SQLite 单文件，两者是同一位置的替代方案 | 有：`RAG-DECISIONS.md` 第 4 节的取舍记录 |
| 3 | 图存储选 SQLite → 单机 compose 与 nginx（depends_on） | 选 SQLite 而非 Neo4j 的直接动因是 2C2G 单机部署的内存与算力约束 | 有：`RAG-DECISIONS.md` 第 4 节的 2C2G 内存账 |
| 4 | 工具消息配对与回填 → OpBatch 原子应用（depends_on） | 工具结果回填后要传入更新后的候选树，依赖 OpBatch 原子应用 | 有：`AGENT_PLAN.md` 的工具协议一节 |
| 5 | 状态机与工具执行 → op 批与原子应用（depends_on） | agent 循环的每次改树都要落成 op 批并原子应用，否则候选与保存版本会串线 | 有 |
| 6 | B 侧交付面 → 后端可调用 agent 循环（part_of） | 生成链路与后端地基归 B，agent 循环是其中一块交付 | 有：`PLAN.md` 的分工表 |
| 7 | A 侧交付面 → 1:10–2:10 画布编辑（part_of） | 画布编辑与布局主题导出归 A，是演示第二段的展示内容 | 有：`PLAN.md` 的 5 分钟演示脚本 |
| 8 | 1:10–2:10 画布编辑 → relations 与视图属性分（depends_on） | 切布局换主题不改语义，正是视图属性与语义结构分离的演示 | 有：`ARCHITECTURE.md` 的"布局与语义分离" |

**8 条全都能在材料里找到依据**，没有一条是"看起来说得通但材料里没有"。这是图谱这条
路最实的一项收益：关系是从抽取出来的边来的，而边带 `source_id` + 偏移，等于每条关系
在构造时就已经锚定在某段原文上。

### 画布上画出来了吗

是。两张截图（`docs/graph-two-pass-canvas.png`、`docs/graph-two-pass-panel.png`）：

- 画布上关系线是**曲线 + 虚线 + 半透明**，按 kind 上色（依赖=蓝、因果=红、冲突=玫红、
  属于=紫、细化=青、引用=灰），中点带中文短标签（「依赖」「属于」「因果」）。曲线而不是
  折线，是因为两端没有共同父节点，折线会在中间节点上拐直角，看起来像"穿过了某个节点"。
- 节点详情里列出这个节点参与的关系：kind 徽标 + "谁 → 谁" + **why 原文** + 删除按钮。
  截图里那个节点有 2 条（属于 / 依赖），全图 14 条。

**没做的**：导出（markdown 一节 / puml 注释）没做，json 本来就保。画布与详情这两处
是"关系有没有显示出来"的唯一判据，导出只是把它带到仓库里。

## 7. 开关与降级

```
MINDMAP_GRAPH_SKELETON=1     # 两段式；不设 = 原三段式（逐字节不变）
```

- **默认关**：这条路依赖 Neo4j 活着且图已建好，而"图没建"在新机器上是常态。
- **只在 `tree` 上开**：流程图的一级是**阶段**（先后来自材料，图上的边没有时间轴），
  鱼骨是六个固定类别（换一套就不是鱼骨图）。
- **图空时退回三段式并记 `GRAPH_SKELETON_UNAVAILABLE`**：静默退回会让覆盖率数字
  莫名其妙地掉回三段式的水平，而用户以为开关生效了。

## 8. 自评：这条路好在哪、差在哪

**好**：

1. **relations 是白拿的**。三段式 `relations` 恒为 0，因为它没有任何地方能表达跨分支
   语义；两段式一次给 12 条，且 why 条条有依据（第 6 节）。
2. **快一倍**：47.6 s vs 96.7 s。
3. **分支更宽**：7 支 vs 4 支。章节骨架被材料的章节结构锁死（那四份文档只有 4 个大
   章节），图谱能给到 7–8 支。注意这**没有**换来覆盖率——分支多了，节点反而少了。

**差**：

1. **覆盖率没上去**，三个口径全不占优。用户想解决的那个"30% 太低"的问题，这条路没解决。
2. **detail 掉了一半**（156 → 77 字）。这是最实质的退化：`detail` 是用户点开节点才看到
   的正文，它从"两段像样的说明"变成了"一句话"。
3. **一级分支名是实体名**（`mindmapcontent`、`sqlite`、`w1`）。实体名是抽取层的产物，
   不是人的组织方式——它比章节标题更贴内容，但**更难读**，而且模型对着一个短实体名
   写不出深度说明（第 5 节那条因果链）。
4. **依赖 Neo4j 与一次建图**。这台机器上建一次图花了 610 秒 / 约 30 万 token。

**结论**：这条路值得留下的部分**只有 relations**。覆盖率与 detail 的退化说明"用图谱
代替章节骨架"这个判断在**这批材料上**不成立——材料本身有清晰章节时，章节就是最好的
骨架。

如果要把这条路的收益留下、代价去掉，方向是**不做二选一**：骨架仍用章节（保留 A 组的
detail 与覆盖率），检索 query 补充图的实体名（提高召回），结构那一次**额外**要求
relations（用第二段之前的那一次调用顺手产出）。那是三段式 + 图谱关系，不是两段式。

## 9. 复现

```bash
set JAVA_HOME=C:\tools\jdk-21.0.12.1+1
D:\neo4j\neo4j-community-5.26.0\bin\neo4j.bat console

# 2. 建图（22 份材料；610 秒 / 179 块 / 1830 实体 / 1381 边）
cd backend
python scripts/ingest_graph_corpus.py --reset --report data/graph-ingest-report.json

# 3. A/B（各 2 次）
set MINDMAP_NEO4J_PASSWORD=***
python scripts/measure_graph_two_pass.py --repeat 2 --save data/ab-two-pass.json
```

0 失败 / 610.4 秒；抽取输入 271,937 字、输出 186,904 字，按 1.5 字/token 折算约
**306k token**（181k 输入 + 125k 输出）。图：1,830 实体 / 1,381 边 / 409 孤立实体。
