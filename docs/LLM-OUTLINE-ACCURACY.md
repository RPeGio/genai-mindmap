# PDF 纯文本交给 LLM 分层：准确率实测

回答一个问题：`pymupdf` 抽出的纯文本交给 DeepSeek 恢复章节树，到底准不准。

## 实验设计

### 金标准从哪来

`en_paper`（Attention Is All You Need，15 页）自带 **22 条 PDF 书签**——
这是论文制作方标注的目录，与任何解析器无关，可以直接当标准答案。另补三条：

| 条目 | 依据 |
|---|---|
| `Abstract` | 正文第 24 行，独立成行 |
| `References` | 正文末尾独立章节 |
| `Attention Visualizations` | 正文第 743 行独立成行 |

合计 **25 条**。文档标题本身（`Attention Is All You Need`）不算章节，不计入。

`cn_doc`（中文 30 页技术文档）无书签，用它自带的《目录》九章作为一级金标准。

### 指标

- **precision** = 模型给出的条目里能对上金标准的比例 —— 衡量**编造**
- **recall** = 金标准里被找到的比例 —— 衡量**漏章节**
- **level_acc** = 对上之后层级一致的比例 —— 衡量**分层本身**
- **order_acc** = 对上之后顺序保持的比例

匹配规则：标题归一化（剥编号、去装饰符与空白）后先做精确匹配，再按
`difflib` 相似度 ≥ 0.85 兜底，一条金标准最多被认领一次。

### 重复

每个 LLM 方案跑 3 次，取中位数。`temperature = 0.2`。

## 结果：en_paper（25 条金标准）

| 方案 | 输出条数 | P | R | F1 | 层级 | 顺序 |
|---|---|---|---|---|---|---|
| **pymupdf + DeepSeek（全文）** | 24 | **1.000** | **0.960** | **0.980** | **1.000** | **1.000** |
| pymupdf + DeepSeek（截断 20000） | 17 | 1.000 | 0.944 | 0.971 | 1.000 | 1.000 |
| pymupdf4llm_noocr（版面分析） | 25 | 1.000 | 1.000 | 1.000 | 0.880 | 1.000 |
| Docling（版面分析） | 27 | 0.889 | 0.960 | 0.923 | **0.500** | 1.000 |
| 正则基线（无 LLM） | 0 | 0.000 | 0.000 | 0.000 | — | — |

三次运行结果**完全一致**，没有方差。

### 逐项读

**pymupdf + DeepSeek：零编造，层级全对。**

24 条输出全部对上金标准，precision = 1.0——没有一个条目是模型凭空造的。
唯一遗漏是 `Abstract`：它在原文里紧跟在作者邮箱块后面，模型把那一整块当成了
标题页的一部分。层级 24/24 全对，顺序 24/24 全对。

**pymupdf4llm 准确率更高，但层级略差且代价大。**

recall 满分（25/25），层级错 3 处（0.88）。代价是 26.4 秒 / 351MB，
而 LLM 链路是 0.19 秒抽文本 + 约 4 秒 API 调用 / 55MB。

**Docling 的层级是废的。**

27 个标题**全部标成 H2**，没有一级、二级、三级的区分。层级准确率 0.5 就是这么来的——
金标准里 10 个一级、12 个二级、3 个三级，全标 H2 等于只能碰对二级那 12 个。
另外它把文档标题和图注 `Input-Input Layer5` 当成了章节，产生 3 个假阳性。

对思维导图来说这是硬伤：**导图的骨架就是层级**，全平铺等于退化成列表。

**正则基线完全失效。**

从 pymupdf 纯文本里按「行首编号 + 标题」找章节，命中 **0 条**。
原因是 PDF 的文本流把编号和标题拆开（`1` 与 `Introduction` 不在同一行），
纯文本里没有任何可靠的行级结构。这条路直接排除。

### 截断的影响

产线 `MAX_INPUT_CHARS = 20000`，en_paper 全文 36882 字符，截断后只剩 18 条金标准可见。

| | 数量 |
|---|---|
| 金标准总数 | 25 |
| 截断后仍在输入里 | 18 |
| 模型找到 | 17 |
| 未能找到范围内的 | 1（`Abstract`） |

**截断范围内 recall = 17/18 = 0.944，precision = 1.0。**
被截掉的 7 条（6 Results 及其后全部章节、References、Attention Visualizations）
模型没有看见，不算它的错——这是产线输入上限造成的确定性损失。

`cn_doc` 更极端：全文 145909 字符，20000 字符只到第 3 章，**后 6 章在输入里根本不存在**。
截断后模型输出了前三章，precision = 1.0、层级 = 1.0，但 recall 只有 0.375。
这不是模型的准确率问题，是输入量的硬限制。

## 结论

**pymupdf + DeepSeek 的章节恢复准确率：precision 100%、recall 96%、层级准确率 100%、顺序准确率 100%。**

相对于本地版面分析的对照：

| | pymupdf + LLM | pymupdf4llm_noocr | Docling |
|---|---|---|---|
| 层级准确率 | **1.000** | 0.880 | 0.500 |
| 编造率 | 0% | 0% | 11.1% |
| 本地耗时 | 0.19s（+4s API） | 26.4s | 115s |
| 峰值内存 | **55MB** | 351MB | 1900MB |

在 2C2G 机器上，LLM 链路不仅内存和耗时占优，**层级准确率还是最高的**——
版面模型能识别"这行字更大更粗"，但判断不了"这是三级小节还是二级小节"，
而这份 PDF 的 3.2.1 / 3.2.2 / 3.2.3 恰恰需要靠编号语义来定级。

## 顺带发现的两个产线缺陷

**一、`chat()` 的 JSON 解析没有容错。**

`backend/app/generation/service.py` 第 79 行是裸 `json.loads(content)`，
prompt 里写着"不要代码围栏"但模型不总听话。本次 18 次调用里出现 1 次带
` ```json ` 围栏，产线直接抛 `GenerationError("模型返回内容不是符合约定的导图 JSON")`。
单次失败率约 5~11%，用户侧表现为随机报错。

修法：解析前剥掉 ` ```json ` / ` ``` ` 围栏，再截取最外层花括号或方括号。

**二、`Abstract` 稳定漏识别。**

三次运行的漏项完全一致，说明不是随机波动。`pymupdf` 抽出的是：

```
Attention Is All You Need
Ashish Vaswani∗
Google Brain
...
illia.polosukhin@gmail.com
Abstract
The dominant sequence transduction models ...
```

`Abstract` 夹在作者块和正文之间，模型倾向于把它连同上方一起归入标题页。
若验收要求摘要进导图，得在 prompt 里显式点名，或给 `Abstract` 单独设一条后处理规则。
