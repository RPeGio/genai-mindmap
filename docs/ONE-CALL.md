# 回到一次生成：骨架 + 每支检索 + 一次写完（→ 后接"只写说明"一段，再拆两半并发）

2026-11-18。`docs/ONE-PATH.md` 那次**只做减法**（删 `full` 形态与整树生成），这次
**把生成加回来**，但接法与当时被删的那一版不同：检索段改成「骨架定好之后每支各检索
一次」（分片那条路一直在用的那套），证据按分支分组一次给模型。

> 后续（同一天）：一次写完把 detail 压到 26–28 字，于是拆出第四步"只写说明"的调用。
> 最终形态是 **骨架 → 每支检索 → 结构 → 只写说明（两次并发，各写一半）**，实测与
> 红线判定见下面的「A 落地：三段式」与「B 落地：说明拆两半」两节。本文前半部分
> 记录的是"一次写完"那一步的实测。

## 为什么要改（三条实测依据）

1. **真实用法 100% 是无材料**。`runs` 里全部 16 次运行 `sources` 都是 0 份；连 goal
   写着"请基于附带的 3 份材料"的那两次也是 0。
2. **分片的唯一真优势用不上**。分片材料覆盖 30.5%、整树（rag 下）5.1%——那个差距
   需要材料才成立。没材料时分片付了全部代价（1+N 次调用），拿到零收益。
3. **分片有结构性缺陷：跨支重复**。根因是每支展开时只看到自己那条标题链，看不到
   兄弟支写了什么（`PLAN_PROMPT` 里"彼此覆盖的范围不重叠"模型根本不听）。库里那三张
   `机器学习的主要方向`（56/56/57 节点）各有 **6 个跨支重复节点**（3 个说法各写 2 遍）。

## 实测：detail 质量是这条路不可行的原因

同一主题 `机器学习的主要方向`，无材料、外部检索关，DeepSeek `deepseek-chat`
（`python scripts/measure_single_call.py` / `--deep`），同机同模型：

| 指标 | 一次生成（5 次采样） | 分片（2 次采样） | 库里 B 图（3 张） |
|---|---|---|---|
| 节点数 | 53 / 54 / 59 / 61 / 62 | 60 / 63 | 56 / 56 / 57 |
| **detail 平均** | **45.3 / 28.0 / 28.5 / 26.2 / 27.4** | **70.1 / 64.8** | **82.2 / 82.2 / 82.1** |
| detail 最短 | 13–32 | 0–48 | — |
| 空话（"简要说明""详见"…） | 0 | 0 | 0 |
| 跨支重复 | **0**（5/5） | 0（本机 2 次） | **6 / 6 / 6** |
| 耗时 | 11.2–15.7 秒 | 17.2–22.5 秒 | — |

三条结论：

- **跨支重复真的没了**（0/5 次）。这条改动的核心收益成立。
- **耗时没有到"3–8 秒"**：11–16 秒。骨架那一次 + 一次长输出，不是两次短调用能压下去的。
- **detail 掉到 26–28 字**（首次 45 字是偶发），是分片（65–82 字）的三分之一。加一句
  "不少于 60 字"进 system 也**没有改善**（28.5 → 26.2，同一个水平），说明瓶颈不是
  提示词，是一次输出里要塞几十段说明。

按预定的红线（平均掉到 40 字以下即不可行）：**这条路按"一次写完"的形态不该做。**

## 为什么这是"注意力"而不是"糊弄"

模型没有写"简要说明""详见教材"这类占位话（空话计数 0），它是**把每段说明写短**。
按一级分支拆开看（一次 62 节点那次）：第 1 支 27.5 字 → 第 5 支 23.6 字，越往后面
越短，但幅度不大——不是崩塌，是整体压缩。

## 有材料时反而成立（这是关键的另一半）

同一套代码，带一份 500 字的《预算管理办法》（`--material`）：

| 指标 | 值 |

| 骨架 | 5 条分支全部来自材料章节（预算审批 / 报销时限 / 采购合规 / 资产处置 / 附则） |
| 检索 | `mode=branch`，每支各一次（6.7 秒） |

| 跨支重复 | 0 |

有证据可抄时，detail 能到 53 字、引用 100% 落地。也就是说：**变短发生在"无材料、
纯凭知识写"那条路上——而那是真实用法的全部**。

## A 落地：三段式（结构一次 + 只写说明一次）

2026-11-18，紧接着上一节。`_generate` 从"三段"变成**四步**，对调用方（模型）来说
仍然是"一次调用拿到整张图"，所以工具描述与 `_generate_spec` 的口径没变：

| 步骤 | 模型调用 | 产物 |
|---|---|---|
| ① 骨架 | 1 | 一级分支（名字 / 颜色 / 图标 / flowchart 的边） |
| ② 检索 | 0（本地与向量） | 每支各一次命中，按支分组进 prompt |
| ③ 结构 | 1 | 节点树 + 短 label + `source_refs`；**detail 一律留空** |
| ④ 只写说明 | 1 | `{"节点id": "说明"}`，按 id 对号写回 `detail` |

### 第三段的提示词（`tools.DETAIL_ONLY_PROMPT`）

只留四件事，长度要求**放在最后一段**（前两轮把它写在中间，实测有节点只写一句）：

```
这一次只写思维导图节点的「说明」，不写结构。……一个都不许增删改名，也不许改动父子关系。
只返回一个 JSON 对象…… 键是节点 id（原样照抄），值是说明正文，例如 {"d1a":"…","d1b":"…"}。
不要写「简要说明」「详见教材」「同上」「可参考」这类占位话；也不要把 label 换个说法重复一遍。
**这一轮不要写 source_refs**：引用已经在结构那一轮按证据定好了，这里再写会与那些引用对不上。

每一段说明写 80–150 字、**至少 3 句完整的话**（不是 3 个短语），少于 3 句就是没写完。
如果这个节点的标题是一串并列的东西（几个算法、几种变体、几类方法、几个阶段），
要逐个说清它们各自做什么、差别在哪，不要只把名字列一遍就收。超过 150 字就挑最关键的两三点。
```

user 消息是"主题 + 每个节点一行 `序号. id=…｜label｜位置：根 / … / 父`"+ 上一轮那份
原文（有材料时）+ 末尾一句自查。**用 id 做键、不靠顺序**：顺序错一位，整棵树的说明会
整体串行错位，而每一段话本身都通顺——从产出上完全看不出来。

### 实测（同一主题 `机器学习的主要方向`，无材料，外部关，deepseek-chat）

12 次采样 = 4 组提示词 × 3 次（`python scripts/measure_single_call.py --repeat 3`）：

| 指标 | 一次写完（旧，5 次） | **三段式（12 次）** | 分片（2 次） | 库里 B 图（3 张） |
|---|---|---|---|---|
| detail 平均 | 45.3/28.0/28.5/26.2/27.4 | **78.9–137.7（均值 105.1）** | 70.1/64.8 | 82.2/82.2/82.1 |
| detail 最短 | 13–32 | 21–77（均值 43） | 0–48 | — |
| 空话 | 0 | 0 | 0 | 0 |
| 跨支重复 | 0（5/5） | 0（最终提示词 3/3；12 次里 4 次出现 3 个「典型应用」） | 0（本机 2 次） | 6/6/6 |
| 总耗时 | 11.2–15.7s | 33.0–59.0s（均值 44.5） | 17.2–22.5s | — |
| 模型调用 | 2 | **3** | 1+N（8–25） | — |

带材料（500 字《预算管理办法》）1 次：50 节点、detail 平均 **117.3**、最短 **93**、
引用 `declared=31 / kept=31`（全部存活）、跨支重复 0、总 51.5 秒
（骨架 1.2 / 结构 7.2 / 说明 36.6，检索 6.6）。

### 红线逐条判定

| 红线 | 结果 |
|---|---|
| detail 平均 ≥ 80 | ✅ 12 次里 11 次 ≥ 89，最低 78.9 |
| 低于 40 判不可行 | ✅ 没有一次落在这个区间（均值 105.1） |
| 最短 ≥ 60 | ❌ 21–77，12 次里 11 次不达标（**有材料时 93，达标**） |
| 空话 0 | ✅（唯一一次"命中"是脚本误报：`如上` 命中了「如上下文学习」，检测词已改） |
| 跨支重复 0 | ⚠️ 最终提示词 3/3 为 0；早期提示词 12 次里 4 次有 3 个「典型应用」重复 |
| 总调用 = 3 | ✅ 每次都是 3（`data.calls` 有骨架/结构/说明三列） |
| 总耗时 < 30 秒 | ❌ 33.0–59.0 秒，一次都没进 30 秒 |

**两条没达标的红线都不是提示词能修的**，理由自带实测：

- **最短 60 写不出来**是"无材料"这条路的特性：偏短的永远是**并列型技术节点**
  （「K-means 与层次聚类」「支持向量机」「常见变体」），模型写一句精确的技术陈述
  （40 字左右）就认为说清了。三组提示词改法（并列项逐个说清 / 至少 3 句 / 要求挪到
  末尾 + user 末尾自查）**全部无效**：最短始终 40–46。而**有材料时最短 93**——同一段
  提示词、同一个模型，差别只在"有没有原文可抄"。
- **30 秒写不进去**是输出量决定的：50 个节点 × 约 100 字 ≈ 3,300 输出 token，实测
  输出侧 13–46 秒（约 90–170 token/s）。要进 30 秒只有两条路，都有代价：
  ①把说明拆成两次**并行**调用（总调用变 4，墙钟约 26 秒）；②削减节点数（每段预算不变
  时输出量线性下降，但那是"图更小"而不是"更快"）。

结论：**这条路成立**（平均 105 字是"一次写完"的 3.5 倍、跨支重复 0、调用 3 次），
但"最短 60 字"与"30 秒"这两条红线在"50 节点 × 100 字 × deepseek-chat"这个组合下
拿不到——它们是**规模与速度**的约束，不是提示词的约束。

### 兜底（`_fill_details` 的八种失败）

| 失败 | 行为 |
|---|---|
| 少返回几个 id | 缺的**保持原样**（多半是空）、`DETAIL_ROUND_INCOMPLETE` 把 label 列出来 |
| 返回不存在的 id | 忽略并计数（`data.detail.unknown_keys`），不静默 |
| 返回空串 / 非字符串 | 当"没给"（`_detail_map`），不编 |
| 整次调用失败 | 树照常交付、`DETAIL_CALL_FAILED`（`detail` 是可选字段） |
| 额度用尽 | 不发这次调用、`DETAIL_SKIPPED_NO_BUDGET` |
| 结构那一次自己写够了 | 不发这次调用（`data.detail.skipped == "nothing_to_fill"`） |
| **一半失败、一半成功** | 成功那半**必须落地**（`asyncio.gather(return_exceptions=True)`），`DETAIL_CALL_FAILED` 说清是第几半 |
| **返回到另一半的 id** | 丢弃并计数：那一半的 user 里没有这个节点的 label 与位置，模型为它写的话是凭空编的 |

**引用不可能被改动**：这一段只从返回值里读 `id → 字符串`，写回的字段只有 `detail`。
`source_refs` 仍是结构那一轮的产物，`EVIDENCE_UNUSED` 的分母不受影响——带材料那次
`declared=31 / kept=31` 就是这条的实测。

界面上另有一帧 `stage="detail"`（开始 / 结束各一帧，与外部检索同形）：这一段要
13–46 秒，而树已经在结构那一次长完了，不推帧的话用户看到的是"树长完了、然后卡住"。


### 自评：第三段看得到 evidence 吗？——看得到，而且必须给

第三段的 user 里**重新附了同一份按支分组的原文**（`DETAIL_ONLY_EVIDENCE_RULES`），
system 里另外一句明说"引用已经定好了，这一轮不要写 source_refs"。两个理由：

1. **错位的风险是真实的**：`verify_source_refs` 只校验"引文逐字在原文里"，**不校验
   说明与引文讲的是不是同一件事**。引用说的是 A、detail 讲的是 B，逐字校验一条都拦
   不住，界面上却是一条看起来有依据的节点。
2. **实测给了正反两面**：带材料那次最短 93 字、`kept=31/31`；无材料时最短 43 字。
   同一段提示词、同一个模型，差别只在"有没有原文可抄"。也就是说 evidence 不只让
   说明更长，还让说明贴着原文写。

代价是输入侧多拼一遍原文（带材料那次结构 7.2 秒、说明 36.6 秒，量级上没有被拖慢），
比"说明与引用脱节"便宜得多。**不加 evidence 是不划算的**。

## B 落地：说明拆两半（3 次调用 → 4 次）

2026-11-18，紧接着 A 那一节。三段式落地之后，剩下的唯一瓶颈是**第 4 步的输出量**：
50–60 个节点 × 100–140 字 ≈ 5,500–8,000 字，输出侧就要 35–45 秒。这一节把第 4 步
拆成**两次并发调用**，各写一半节点。骨架与结构一步没动。

| 步骤 | 改前 | 改后 |
|---|---|---|
| ① 骨架 | 1 | 1 |
| ② 检索 | 0 | 0 |
| ③ 结构 | 1 | 1 |
| ④ 只写说明 | 1（全部节点） | **2（各一半，并发）** |
| 合计 | 3 | **4** |

### 怎么分两半（`tools._split_nodes`）

**按节点数均分，切点吸附到父边界。**

两个候选的算术差别是可以算出来的：56 个节点按支分是"3 支 33 个 / 2 支 23 个"，
慢的那半要多写 43% 的输出，而 `asyncio.gather` 的总墙钟看的就是最慢的那次——按支分
等于把 21 秒退回 30 秒。按节点数均分则是 28/28。**墙钟由输出量决定，不由调用次数
决定**，所以均衡优先。

"同一支一起写更连贯"这个好处不能全丢，但它有一个更便宜的拿法：**切点不落在某个
父节点的孩子列表中间**。前序里同一父的孩子必然连续，所以"与上一项的 path 不同"就是
换了一个父节点；切点在中点附近 ±`count/8` 位内找最近的边界，找不到（例如整棵树是
"根 + 56 个并列一级子节点"）就直接按中点切——那种形状本来就没有"兄弟要互相区分"
的单元。

实测这次的三棵树：51 个待补切 25/26、46 个切 23/23、64 个切 32/32。均分误差 0–1 个。

**小于 `DETAIL_SPLIT_MIN`（12）个节点不拆**：两次首 token 延迟（1–2 秒）加两份
system 提示词是固定成本，10 个节点的一半只有 5 段说明，模型预热的时间比写 5 段还长。

### 并发安全

- **额度**：`ctx.reserve_model_call()` 读-判-写之间没有 `await`，在 asyncio 的单线程里
  不会被切走，两半各占一次不会算错。但"不会算错"之外还有一件更要紧的事——**只剩一份
  额度时该写哪一半**：交给调度器（谁先跑到谁拿）就成了不确定行为。所以额度在
  `gather` **之前串行占完**，够几份写几半，`extra_model_calls` 跟着各加一次（与
  `reserve` 同增量，`service._loop` 的对账不会重复补记）。
- **失败隔离**：`asyncio.gather(..., return_exceptions=True)`。一半 500、另一半照样落地
  ——没有这一条，一次 500 就把另一半已经写好的二十几段话一起丢掉，那比不拆更糟
  （不拆时只有一次失败面）。
- **取消**：`return_exceptions=True` 会把 `CancelledError` 一起收进返回值。`_settle_halves`
  第一件事就是把它重抛——吞掉它等于让 `max_seconds` 超时与用户中途取消失效：工具还在
  跑、模型请求还在计费，而 `_run_tool` 以为已经停了。
- **输入**：两半各带一份完整原文（节点清单各占一半）。每次请求的输入**比单次更小**，
  所以 `ensure_input_within_context` 只会更松；翻倍的只是计费侧的 token。**没有按支
  过滤原文**：过滤需要一个"每段原文对应哪一支"的可靠映射，做错的表现是"说明与证据
  对不上"——那是这条路最隐蔽的失败面，省下的输入量不值这个风险。

### 合并

- **两半的 id 天然不相交**，不需要运行时去重：`_detail_map` 按各半自己的 id 清单过滤，
  不在清单里的键一律进 `unknown`、不进 `applied`。
- **越界的 id 必须丢**：模型返回到另一半的节点时，那一半的 user 里没有这个节点的
  label 与位置，它写的话是凭空编的，却长得完全像一段正常说明。
- `data["detail"]["seconds"]` 是**墙钟**（两半取大的那个），不是两次之和——那正是这次
  改动要的答案。每半各自的秒数在 `halves` 里。
- `DETAIL_ROUND_INCOMPLETE` 拆过时按半报：`第 1 半只写回 22/25（缺 3 个：「…」）；第 2 半齐全`。
  "没额度"与"调用失败"这两种**根本没发出请求**的情形与"模型少写了"分开列。

### 实测（同一主题 `机器学习的主要方向`，无材料，外部关，deepseek-chat，各 3 次）

对照的两组跑在**同一份代码、同一个模型**上：把 `DETAIL_SPLIT_MIN` 顶到天上就是"拆

| 结构 | 13.92（14.72 / 13.17 / 13.84） | 11.81（9.79 / 11.65 / 13.99） | — |

原因，输出量本身不是。

### 两半的风格分叉吗——不分叉，有数据

三次采样，两半的"起手腔调"都不分叉：

| 采样 | 模板化指称（半 1 / 半 2） | 每段句数（半 1 / 半 2） | 平均字数（半 1 / 半 2） |
|---|---|---|---|
| #1 | 0 / 0 | 3.2 / 3.0 | 144.8 / 122.0 |
| #2 | 0 / 0 | 3.0 / 3.6 | 136.6 / 120.9 |
| #3 | 0 / 0 | 4.3 / 4.0 | 158.9 / 173.2 |

判据是**模板化指称**（`本部分` / `这一节` / `该节` / `这里` / `首先` / `总之` …共 27 个
词，只要出现在说明**开头**就计一次）——"一半写「本部分规定…」、另一半写「这一节讲…」"
正是它。**两半各 0 次**：这个模型压根不用这套腔调，两半都没有，也就不存在各用一套。

两个补充口径，都不是"感觉上没问题"：

1. **剥掉 label 后的起手二字**：两半各有几个"只在自己这边出现"的 pattern
   （#1 一个「深度」、#2 两个「无监」「监督」、#3 七个），但那些全是**内容**——两半
   写的是不同的节点，开头当然不同。把 label 剥掉之前，第一版度量报出 4–6 个"独占
   起手"，全是「监督」「关联」「强化」这些 label 开头：那是自己给自己造的假警报。
2. **两半的长度差落在采样波动内**：两半之间的平均字数差是 22.8 / 15.7 / 14.3 字，
   而**同一配置三次采样之间**的差是 118.2 / 112.1 / 126.3（极差 14.2 字）。也就是说
   "两半的差异"没有超出"同一件事重复做的差异"——而且三次里哪半更长不一致（两次半 1、
   一次半 2），没有系统性偏移。

**这条结论的边界**：3 次采样够看出"两半都完全不用模板腔调"，不够排除"某个特定两半
组合会分叉"。要更强的结论需要 10 次以上采样；脚本已经把这一列常驻化
（`scripts/measure_single_call.py` 的 `style.diverged`），重新采样不需要改代码。

判据本身也有一处覆盖不到：`diverged` 只看**模板腔调**。一半写 300 字、另一半写 80 字
那种"量"上的分叉，它判不出来——那由同一张表里的"每段句数"与"平均字数"两列兜着
（本次两半的句数差 0.2–0.6、字数差 14–23 字）。真正的风险是"一半短一半长"读起来
像两个人写的，所以这两列必须一起看，不能只看 `diverged`。

### 没拿到 30 秒：33–39 秒，说明仍占大头

三次是 33.25 / 33.20 / 49.93，均值 **38.79**（拆之前 54.83）。**没有一次进 30 秒**，
偏快的那两次（33.2）也差 3 秒。

原因不是拆分失效，而是**每次要写的字比估算的多**：

| 采样 | 总字（节点 × 平均） | 说明那步 | 折算 |
|---|---|---|---|
| 拆前 #1 | 46 × 118.2 = 5,437 | 38.82s | 140 字/s |
| 拆前 #3 | 59 × 126.3 = 7,452 | 44.76s | 167 字/s |
| 拆后 #1（慢半） | 25 × 144.8 = 3,620 | 21.99s | 165 字/s |
| 拆后 #3（慢半） | 32 × 173.2 = 5,542 | 33.58s | 165 字/s |

**生成速度稳定在 140–170 字/秒**（含首 token 延迟），所以墙钟基本等于 `最慢那半的字数
÷ 160`。原来估"26 秒"用的是"56 × 105 = 5,900 字，一半 2,950 字"；实测这批树是
48–65 个节点、每段 127–166 字，一半就是 3,600–5,500 字——**算术没错，输入量变了**。
#3 那次尤其明显：detail 平均 166 字（已超 `DETAIL_MAX_CHARS=150` 的上限），一半要写
5,000 字以上，33.6 秒是它应得的。

第二笔是**结构那一步的 11.8 秒是常量**：骨架 1.8 + 结构 11.8 = 13.6 秒，与说明那一段
无关。说明那一步即便压到 20 秒，总数也是 33.6。

三条能进 30 秒的路，代价都写清楚：

| 走法 | 推算 | 代价 |
|---|---|---|
| 拆**三**份（每份约 17–22 个节点 ≈ 2,500 字） | 2,500/160 ≈ 16 秒 + 首 token ≈ 17.5s，总 **31 秒** | 5 次调用；原文带三份；两两之间的风格一致性从 1 对变成 3 对 |
| 拆**四**份（每份约 14 个 ≈ 2,000 字） | 约 13 秒，总 **27 秒** | 6 次调用；同上，且小树上退化明显（14 个节点是 `DETAIL_SPLIT_MIN` 附近） |
| 把 `DETAIL_MAX_CHARS` 从 150 降到 110 | 平均落回 110 字 → 一半约 2,800 字 ≈ 19 秒，总 **33 秒** | detail 平均从 142 掉到 ~110（仍高于 80 红线），而且"最短 60"这条可能一起掉 |

**建议按现状收（33–39 秒 / 142 字）**：它比拆之前快 30%、detail 还长了 20%，而"30 秒"
这条红线现在只差 3–9 秒——为了这点差距再拆一份，换的是 3 对风格一致性与一次小树
退化。真要压到 30 秒以内，**拆四份**是把这条红线换成事实的唯一走法，但那是另一个
决定，不该混在这次改动里。

### 前端：帧仍然是两帧，"正在给 56 个节点写说明"

帧由 `_fill_details` **统一推**，两半自己不推。理由不是省事：

- `stageText` 是覆盖式单值（`stores/mindmap.ts` 的 `case 'stage'`）。两半各推一帧
  "正在给 28 个节点写说明"，用户看到的是同一句话闪两遍；
- 更要紧的是**结束帧**：两半各推"已写完 28 个节点的说明"，而总共 56 个——先回来的
  那一半会把界面上那句改成一个**在那一刻不成立**的结论。谎报比不报更糟。

所以计数一律用**切半前**的总数，帧数与文案与拆分之前**逐字相同**（开始一帧、
结束一帧），前端一行没改。两半各自的秒数与节点清单在 `data.detail.halves` 里，
需要细粒度信息的人从那里读。

## C 落地：两级骨架（一级分支太多时先归成几组）

`branches` 的上限从 8 提到 20 只把"塞进一支"换成了"图很宽"：二十节的材料就是二十条
一级分支。这一次把分组提前到**骨架那一次调用**里——不是生成之后再聚类。

| 触发 | 组数 | 契约 |
|---|---|---|
| `max(args.branches, 目录行数) > SKELETON_GROUP_THRESHOLD`（10） | 每组 4 支倒推，夹在 3–6（20 节 → 5） | `{"groups":[{"label","color","icon","children":[{"label"}]}]}` |

- **判据只影响"要不要问"，不影响成不成功**：判多（要了两级、回来只有 8 支）→
  `_skeleton_plan` 压平；判少（要了扁平、回来 20 支）→ 与改动之前逐字节相同。
- **老形状照收**：`{"branches":[…]}` 仍然解析成一层。该分组时模型仍回扁平，退化成
  不分两级，**不判失败**——骨架已经花掉了。
- **不多花调用**：那句要求拼在同一次骨架请求的 system 里（`_group_plan_rules`，
  前缀仍是 `PLAN_PROMPT`，逐字节回归用例不受影响）。
- **组节点一次调用都不吃**：检索仍按二级分支各一次、结构仍是那一次、第三段仍按节点数
  切两半；组既不在 `titles` 里，也不进 detail 清单（`skip_ids`）。
- **形状兜底**：模型仍写成二十条并列时，`_apply_groups` 按骨架的分组摆正（只搬位置、
  不改 label/detail/引用），记一条 `SKELETON_GROUPS_APPLIED`。
- **颜色**：一级色只落在分组上，二级由前端沿父链继承（`mindmap.ts::inheritedColor`，
  前端一行没改）。

## 自评：分两级之后，"跨支重复"会不会回来

**这条路上不会**，理由是结构而不是运气：跨支重复的成因是"每支只看得见自己那条标题链"
（分片那条路的病）。`_generate` 的结构那一步是**一次调用写整棵树**，输入里就有全部
二十节与五组、以及按支分好的全部证据——分组没有把这次写拆开，它只是让模型的产出多
一层。实测三次 arm 各 2 轮，跨支重复都是 0。

**分组还顺带堵住了一条新路**：同一支被列进两个组时，`_cap_plan` 只认第一次出现的
那一组（判据与 `_cross_branch_duplicates` 同源的空白折叠），所以"组 A 的支"和"组 B
的支"从骨架这一层就不可能是同一个节点。

**真正会把它带回来的是另一件事**：如果哪天把 `mindmap_generate_deep`（每支一次调用）
重新注册成主路径，重复就会照旧出现——那是并发展开的代价，与分组无关。所以真要恢复
那条路，先看它的 `CROSS_BRANCH_DUPLICATE`，别看这条表。

## 自评：`expandable` 三态在整树路径上的语义变了

分片那条路里，`expandable` 是**模型的判断**：每次展开的响应里，模型顺手说一句"这个
子项还能不能再拆"，代码按它决定还问不问下一层。一次生成没有"每支的响应"，模型只
能一次声明全部——所以这条路**根本不向模型要这个字段**（`DETAIL_PROMPT` 的格式里
没有它），落树时由 `_stamp_expandable` 按结构事实写：

- 被 `INITIAL_MAX_NODES` 裁掉的节点 → `unknown`（没长完，还能再点）；
- 深度到契约上限（8 层）→ `no`（结构上不可能再加）；
- 其余 → `yes`。

于是三态从"模型判断 + 结构事实"退化成**纯结构事实**。这与契约里那句"这是给界面画
按钮用的状态，不是给模型看的信号"（`contracts/mindmap.py` 的 `NODE_EXPANDABLE`）
是一致的，但**少了一个信息**：模型说过"到底了"的那一档没有了。用户点开一个 `yes`
的叶子，模型可能回"没有更多内容"。分片那条路能少一次这样的空点击，一次生成不能。
